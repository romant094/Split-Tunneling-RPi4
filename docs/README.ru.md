# RPi VPN Gateway

Raspberry Pi 4 настроен как VPN-шлюз с раздельной маршрутизацией: весь трафик, не относящийся к российским IP-диапазонам, выходит через туннель AmneziaWG; российские IP-диапазоны выходят напрямую через провайдера. Для всех устройств в LAN работа шлюза прозрачна.

---

## Как это работает

RPi выступает шлюзом по умолчанию для всех устройств в локальной сети. Весь исходящий трафик проходит через RPi, который делит его на два пути:

- **Трафик не к RU-адресам** выходит через VPN-туннель AmneziaWG (`awg0`).
- **Российские IP-диапазоны** (загружаются ежедневно с `russia.iplist.opencck.org`) выходят напрямую через шлюз провайдера (роутер по адресу `192.168.1.1`).
- **Пользовательские исключения** (`/etc/white-list-extended.txt`) позволяют принудительно направить дополнительные CIDR через провайдера.
- **Маршрут к VPN-серверу** (`YOUR_VPN_SERVER_IP/32`) всегда сохраняется через провайдера, чтобы не возникало петли маршрутизации.

Устройства в LAN получают RPi как шлюз по умолчанию через DHCP-опцию на роутере. Индивидуальная настройка устройств не требуется — разделение трафика полностью прозрачно.

```
Интернет
  ↓
Роутер (192.168.1.1) — подключение к провайдеру
  ↓ eth0
RPi4 (192.168.1.254) — VPN-шлюз
  ↓
Устройства в LAN (шлюз по умолчанию = 192.168.1.254 через DHCP роутера)

Маршрутизация трафика:
  Не-RU → awg0 → AmneziaWG VPN (endpoint: YOUR_VPN_SERVER_IP:36348)
  RU-подсети + исключения → eth0 → провайдер напрямую (через 192.168.1.1)
```

Переменные окружения (из `/etc/vpn-gateway.env` на RPi; источник — `.env` в этом репозитории):

| Переменная | Значение | Описание |
|------------|----------|----------|
| `RPI_LAN_IP` | `192.168.1.254` | IP-адрес RPi в локальной сети |
| `KEENETIC_GW` | `192.168.1.1` | Шлюз провайдера (ваш роутер) |
| `VPN_SERVER_IP` | `YOUR_VPN_SERVER_IP` | IP-адрес endpoint-а AmneziaWG |
| `VPN_IFACE` | `awg0` | Имя VPN-интерфейса туннеля |
| `LAN_SUBNET` | `192.168.1.0/24` | Подсеть локальной сети |
| `RU_SUBNET_URL` | `https://russia.iplist.opencck.org/?format=text&data=cidr4` | Источник списка RU-подсетей в формате CIDR |
| `CRON_UPDATE_HOUR` | `5` | Час (0–23) ежедневного обновления подсетей через cron |

## Требования и подготовка

### SSH-псевдоним

`deploy.sh` подключается к RPi через SSH-псевдоним `pi4`. Добавьте следующее в `~/.ssh/config` на вашем Mac:

```
Host pi4
    HostName 192.168.1.254
    User ar
    IdentityFile ~/.ssh/id_ed25519
```

Проверка: `ssh pi4 "echo ok"` — должна выполниться без запроса пароля. `deploy.sh` использует `BatchMode=yes`, который блокирует переход к вводу пароля.

### Ключи и .env.secrets

VPN-ключи (приватный, публичный и preshared) хранятся в `.env.secrets` (файл добавлен в .gitignore — никогда не коммитится).

```bash
cp .env.secrets.example .env.secrets
# Отредактируйте .env.secrets и заполните три ключа:
#   AWG_PRIVATE_KEY=<44-символьный base64>
#   AWG_PUBLIC_KEY=<44-символьный base64>
#   AWG_PRESHARED_KEY=<44-символьный base64>
```

Каждый ключ должен быть валидной 44-символьной строкой base64 (43 алфавитно-цифровых символа + один символ `=` для выравнивания). Перед любой удалённой операцией `deploy.sh` проверяет все три ключа.

`deploy.sh` генерирует `awg0.conf` из шаблона `amnezia.key.template.txt`, заменяя плейсхолдеры `{{PrivateKey}}`, `{{PublicKey}}` и `{{PresharedKey}}` значениями из `.env.secrets` через sed. Сгенерированный конфиг записывается во временный файл с правами 600 и копируется по SCP в `/etc/amnezia/amneziawg/awg0.conf` (права 600, root:root) на RPi.

### DHCP на роутере

После полного развёртывания и проверки RPi настройте роутер, чтобы он объявлял RPi как шлюз для LAN:

1. Откройте веб-интерфейс роутера: `http://192.168.1.1`
2. Домашняя сеть → Сегменты → По умолчанию → Параметры IP
3. Установите **Адрес шлюза** равным `192.168.1.254`
4. Сохраните

После сохранения устройства в LAN начнут использовать RPi как шлюз при следующем обновлении DHCP-аренды. Для немедленного применения — переподключите Wi-Fi или выполните `ipconfig /renew` на Windows.

**DNS для разрешения доменных имён:** Чтобы в `vpn-status.sh` отображались имена доменов, также установите DNS-сервер в роутере:

1. Домашняя сеть → Сегменты → По умолчанию → DNS-сервер
2. Установите значение `192.168.1.254` (dnsmasq на RPi)
3. Сохраните

Без этого шага в столбце DOMAIN вывода `vpn-status.sh` будут отображаться только IP-адреса.

**Откат:** Очистите поле адреса шлюза в настройках роутера (установите обратно пустое значение или `192.168.1.1`).

## Развёртывание

`deploy.sh` — единственный оркестратор развёртывания. Он выполняет 23 шага последовательно с вашего Mac, подключаясь к RPi по SSH. Во время первоначальной установки вы не запускаете отдельные скрипты вручную.

### Группы шагов

| Группа | Шаги | Что происходит |
|--------|------|----------------|
| Предварительные проверки | 1–3 | Проверка обязательных локальных файлов, загрузка `.env` + `.env.secrets`, валидация ключей, проверка SSH-подключения |
| Установка AmneziaWG | 4 | Потоковая передача `scripts/install-awg.sh` по SSH на RPi; сборка DKMS может занять 10–30 минут |
| Развёртывание конфигурации | 5–9 | Генерация и развёртывание `awg0.conf` (права 600), развёртывание `vpn-gateway.env` (права 644), проверка файлов после развёртывания |
| Развёртывание маршрутизации | 10–11 | SCP-копирование `routing.sh` в `/etc/routing.sh`, активация раздельной маршрутизации (если не указан `--no-run`) |
| Автозапуск | 12–13 | Развёртывание `vpn-routing.service`, перезагрузка systemd, включение `awg-quick@awg0` + `vpn-routing.service` при загрузке |
| Cron + откат | 14–16 | Развёртывание `update-vpn-routes`, запись `/etc/cron.d/vpn-routes` (ежедневно в `CRON_UPDATE_HOUR:00`), развёртывание `vpn-rollback.sh` |
| Логирование | 17–20 | Установка dnsmasq (до развёртывания конфига), развёртывание `dnsmasq.conf`, развёртывание `vpn-status.sh`, развёртывание `watch-routes.py` |
| Исключения + NM | 21–22 | Условное развёртывание `white-list-extended.txt` (если файл присутствует); развёртывание NM-диспетчера `10-vpn-routes` |
| Финальная активация | 23 | Повторный запуск `routing.sh` для применения всех правил iptables LOG и маршрутов исключений |

### Команды запуска

Полное развёртывание (развернуть все файлы + активировать маршрутизацию):

```bash
./deploy.sh
```

Развёртывание без активации маршрутизации (используйте при первом развёртывании до поднятия туннеля или при тестировании изменений конфигурации без изменения активных маршрутов):

```bash
./deploy.sh --no-run
```

Если был использован `--no-run`, активируйте маршрутизацию вручную позже:

```bash
ssh pi4 "sudo /etc/routing.sh"
```

### Примечание об установщике AmneziaWG

Шаг 4 `deploy.sh` передаёт `scripts/install-awg.sh` по SSH и запускает его на RPi от имени root. Вы не вызываете `install-awg.sh` напрямую — это внутренний установщик на стороне RPi, который вызывается только оркестратором развёртывания.

### Поднятие туннеля (ручной шаг)

Поднятие туннеля **не автоматизировано** в `deploy.sh`. `awg-quick up` не идемпотентен — если интерфейс уже существует, команда вернёт ошибку. Запускайте вручную после развёртывания:

```bash
# Поднять VPN-туннель
ssh pi4 "sudo awg-quick up awg0"

# Проверить рукопожатие с пиром
ssh pi4 "sudo awg show"
```

Если туннель уже поднят, сначала опустите его:

```bash
ssh pi4 "sudo awg-quick down awg0 && sudo awg-quick up awg0"
```

## Проверка маршрутизации

Выполняйте эти проверки на RPi через SSH. Все команды требуют `sudo` или запускаются от root.

### 4 проверки маршрутизации

```bash
# 1. Маршрут по умолчанию должен идти через VPN-туннель
ssh pi4 "ip route show default"
# Ожидаемый вывод содержит: default dev awg0

# 2. Зарубежный IP (8.8.8.8) должен маршрутизироваться через VPN
ssh pi4 "ip route get 8.8.8.8"
# Ожидаемый вывод содержит: dev awg0

# 3. Российский IP (77.88.8.8 — Яндекс) должен маршрутизироваться через провайдера
ssh pi4 "ip route get 77.88.8.8"
# Ожидаемый вывод содержит: via 192.168.1.1

# 4. IP VPN-сервера должен маршрутизироваться через провайдера (защита от петли)
ssh pi4 "ip route get YOUR_VPN_SERVER_IP"
# Ожидаемый вывод содержит: via 192.168.1.1
```

### Проверка правил iptables LOG

```bash
ssh pi4 "sudo iptables -L FORWARD -n -v | grep LOG"
# Ожидаемый вывод: два правила LOG — [VPN] на awg0, [ISP] на eth0
```

### Быстрая проверка vpn-status.sh

После генерации трафика в LAN выполните:

```bash
ssh pi4 "sudo /etc/vpn-status.sh"
```

Пример вывода:

```
TIMESTAMP            SRC-IP             DST-IP             DOMAIN                                   PATH
-------------------- ------------------ ------------------ ---------------------------------------- ----
May 23 11:36:21      192.168.1.175      17.248.209.64      apple.com                                VPN
May 23 11:36:22      192.168.1.175      77.88.8.8          yandex.ru                                ISP
May 23 11:36:23      192.168.1.100      104.64.0.0         store.steampowered.com                   VPN
```

Если в столбце DOMAIN отображаются IP-адреса, установите DNS на роутере равным `192.168.1.254` (см. раздел «Требования и подготовка»).

### Проверка автозапуска

```bash
ssh pi4 "systemctl is-active awg-quick@awg0"       # ожидается: active
ssh pi4 "systemctl is-active vpn-routing.service"  # ожидается: active
ssh pi4 "systemctl is-enabled awg-quick@awg0"      # ожидается: enabled
ssh pi4 "systemctl is-enabled vpn-routing.service" # ожидается: enabled
```

## Мониторинг и логи

### vpn-status.sh

`/etc/vpn-status.sh` читает journald в поисках записей iptables с метками `[VPN]`/`[ISP]`, сопоставляет их с журналом запросов dnsmasq для разрешения IP-адресов назначения в доменные имена (с резервным rDNS-поиском через `host`) и выводит человекочитаемую таблицу соединений.

Должен запускаться от `sudo` — читает ядерный журнал и логи dnsmasq.

```bash
ssh pi4 "sudo /etc/vpn-status.sh"
ssh pi4 "sudo /etc/vpn-status.sh --via=vpn --last=100"
ssh pi4 "sudo /etc/vpn-status.sh --device=192.168.1.50 --filter=steam"
```

Все флаги можно комбинировать: `--last`, `--filter`, `--device`, `--via` работают вместе в любом сочетании.

### watch-routes.py

`/etc/watch-routes.py` — обогатитель логов iptables в реальном времени. Запускает `journalctl -f -k` и разбирает строки `[VPN]`/`[ISP]` по мере их появления, разрешая IP-адреса назначения через кешированные rDNS-запросы. Для остановки нажмите Ctrl+C.

```bash
ssh pi4 "sudo /etc/watch-routes.py"
ssh pi4 "sudo /etc/watch-routes.py --src 192.168.1.50 --tag VPN"
```

### journald

Прямые запросы к ядерному журналу без `vpn-status.sh`:

```bash
# Последние 50 решений ядра о маршрутизации
ssh pi4 "sudo journalctl -k -n 50 --no-pager | grep -E '\[VPN\]|\[ISP\]'"

# События запуска/остановки vpn-routing.service
ssh pi4 "sudo journalctl -u vpn-routing -n 50 --no-pager"

# Лог ежедневного обновления подсетей
ssh pi4 "sudo journalctl -t vpn-routes -n 20 --no-pager"

# События восстановления маршрутов NM-диспетчером (после смены carrier)
ssh pi4 "sudo journalctl -t vpn-routes -n 5 --no-pager"
```

### Примечание о DNS

`dnsmasq` на RPi (`192.168.1.254`) должен быть установлен как DNS-сервер в вашем роутере, чтобы разрешение доменных имён работало в `vpn-status.sh`. Без этого все DNS-запросы уходят напрямую к вышестоящему резолверу, минуя журнал запросов dnsmasq, и в столбце DOMAIN будут отображаться только IP-адреса.

## Пользовательские исключения

Используйте этот процесс, когда трафик, который должен выходить через провайдера, уходит через VPN. Типичный случай: сервис (игровой сервер, CDN, стриминговая платформа), IP-диапазон которого не входит в список RU-подсетей.

### Пошаговый процесс: обнаружение → развёртывание

**Шаг 1: Определите трафик, уходящий через VPN вместо провайдера**

```bash
ssh pi4 "sudo /etc/vpn-status.sh --via=vpn"
```

Найдите домены или IP-адреса, которые должны маршрутизироваться через провайдера. Запишите IP-адреса назначения.

**Шаг 2: Определите CIDR по IP-адресу**

Используйте `whois` или `ipinfo.io`, чтобы найти блок сети, которому принадлежит IP:

```bash
whois <ip-адрес-назначения>
# Ищите поле "route:" или "CIDR:", например 23.55.0.0/16
```

Также можно открыть `https://ipinfo.io/<ip-адрес-назначения>` в браузере.

**Шаг 3: Создайте файл исключений**

```bash
cp configs/white-list-extended.txt.example configs/white-list-extended.txt
```

Отредактируйте `configs/white-list-extended.txt` и добавьте ваши CIDR (по одному на строку):

```
# Правила формата:
# - По одному CIDR на строку (например, 23.55.0.0/16)
# - Комментарии только на целую строку (строки, начинающиеся с #)
# - НИКАКИХ встроенных комментариев после CIDR — ip route add отклонит строку
# - Без меток, без лишних пробелов после CIDR
23.55.0.0/16
95.181.176.0/22
```

Примечание: `configs/white-list-extended.txt` добавлен в .gitignore и не будет закоммичен. `.example`-файл (который закоммичен) документирует формат.

**Шаг 4: Разверните**

```bash
./deploy.sh
```

Шаг 21 копирует `configs/white-list-extended.txt` по SCP в `/etc/white-list-extended.txt` на RPi. Шаг 23 повторно запускает `routing.sh`, который загружает маршруты исключений на шаге 5b.

**Шаг 5: Проверьте**

```bash
ssh pi4 "ip route get <ваш-ip-исключения>"
# Ожидаемый вывод содержит: via 192.168.1.1
```

Затем подтвердите в `vpn-status.sh`:

```bash
ssh pi4 "sudo /etc/vpn-status.sh --via=isp"
# Трафик вашего исключения должен теперь отображаться здесь
```

## Откат

`/etc/vpn-rollback.sh` полностью отменяет работу VPN-шлюза одной идемпотентной командой.

```bash
ssh pi4 "sudo /etc/vpn-rollback.sh"
```

### Что удаляет откат

- Останавливает и отключает `vpn-routing.service` и `awg-quick@awg0`
- Останавливает и отключает `dnsmasq`
- Сбрасывает все маршруты на `awg0` и маршрут к VPN-серверу
- Удаляет правила iptables MASQUERADE на `awg0` + `eth0`
- Удаляет правила iptables FORWARD ACCEPT и LOG
- Удаляет `/etc/cron.d/vpn-routes`
- Удаляет `/etc/white-list-extended.txt` (если присутствует)
- Восстанавливает маршрут по умолчанию через `KEENETIC_GW` (`192.168.1.1`)

### Что откат сохраняет

- `/etc/amnezia/amneziawg/awg0.conf` (права 600) — конфиг VPN сохраняется для повторной активации
- `/etc/routing.sh` — скрипт остаётся на диске
- `/etc/white-list.txt` — загруженный список RU-подсетей сохраняется
- Пакеты AmneziaWG — не удаляются

Примечание: `/etc/dnsmasq.conf` и `/etc/vpn-status.sh` остаются на диске, но dnsmasq останавливается.

### После отката

Верните шлюз DHCP на роутере обратно на `192.168.1.1`:

1. Откройте веб-интерфейс роутера: `http://192.168.1.1`
2. Домашняя сеть → Сегменты → По умолчанию → Параметры IP
3. Очистите поле «Адрес шлюза» (или установите `192.168.1.1`)
4. Сохраните

### Повторная активация после отката

```bash
./deploy.sh
```

Развёртывание переустанавливает всё. Существующий `awg0.conf` на RPi перезаписывается свежей версией, сгенерированной из шаблона и `.env.secrets`.

## Справочник по скриптам

### deploy.sh

**Синтаксис:** `./deploy.sh [--no-run]`

Запускается с вашего Mac. Подключается к RPi через `SSH_HOST=pi4` (из `.env`). 23 шага. Загружает `.env` и `.env.secrets`; проверяет ключи перед любой удалённой операцией.

**Флаги:**

| Флаг | Описание |
|------|----------|
| `--no-run` | Развернуть все файлы, но пропустить активацию `routing.sh`. Используйте при первом развёртывании до поднятия туннеля или при тестировании изменений конфигурации без активации маршрутов. |

**Примеры:**

```bash
# Полное развёртывание + активация маршрутизации (стандартное использование)
./deploy.sh

# Только развёртывание — активировать маршрутизацию вручную позже
./deploy.sh --no-run

# Активировать маршрутизацию после развёртывания с --no-run
ssh pi4 "sudo /etc/routing.sh"
```

### scripts/routing.sh (развёртывается в /etc/routing.sh)

**Синтаксис:** `sudo /etc/routing.sh [--no-update]`

Сброс и перестройка раздельной маршрутизации. Идемпотентен — безопасно запускать повторно в любой момент.

При каждом запуске: загружает RU-подсети с `RU_SUBNET_URL` → сбрасывает существующие VPN-маршруты → добавляет маршрут к VPN-серверу → добавляет маршруты RU-подсетей через `KEENETIC_GW` → загружает `/etc/white-list-extended.txt` (если присутствует) → устанавливает маршрут по умолчанию через `awg0` → настраивает MASQUERADE и правила iptables LOG → сохраняет через `iptables-save`.

Загружает переменные из `/etc/vpn-gateway.env`.

**Флаги:**

| Флаг | Описание |
|------|----------|
| `--no-update` | Пропустить загрузку свежего списка RU-подсетей; использовать существующий `/etc/white-list.txt`. Безопасно, когда файл подсетей актуален. Используется `update-vpn-routes` после атомарной замены файла, чтобы избежать двойной загрузки. |

**Примеры:**

```bash
# Полный запуск с загрузкой свежего списка RU-подсетей
ssh pi4 "sudo /etc/routing.sh"

# Перестройка маршрутов с существующим файлом подсетей (без загрузки)
ssh pi4 "sudo /etc/routing.sh --no-update"

# Проверить результат
ssh pi4 "ip route show default"     # ожидается: default dev awg0
ssh pi4 "ip route get 8.8.8.8"      # ожидается: dev awg0
ssh pi4 "ip route get 77.88.8.8"    # ожидается: via 192.168.1.1
```

### scripts/vpn-status.sh (развёртывается в /etc/vpn-status.sh)

**Синтаксис:** `sudo /etc/vpn-status.sh [--last=N] [--filter=STRING] [--device=IP] [--via=vpn|isp]`

Читает записи `[VPN]`/`[ISP]` из journald, сопоставляет с журналом запросов dnsmasq для разрешения доменных имён, использует rDNS (`host`) как резервный метод. Столбцы вывода: `TIMESTAMP SRC-IP DST-IP DOMAIN PATH`.

Должен запускаться от `sudo`.

**Флаги:**

| Флаг | Описание |
|------|----------|
| `--last=N` | Показать последние N записей ядерного журнала (по умолчанию: 50) |
| `--filter=STRING` | Поиск без учёта регистра по частичному совпадению в столбце DOMAIN |
| `--device=IP` | Фильтр по IP-адресу исходного LAN-устройства (поле SRC) |
| `--via=vpn\|isp` | Показывать только соединения, маршрутизируемые через VPN или ISP; комбинируется с другими фильтрами |

Все флаги комбинируются свободно.

**Примеры:**

```bash
# Показать последние 50 соединений (по умолчанию)
sudo /etc/vpn-status.sh

# Показать последние 100 соединений через VPN
sudo /etc/vpn-status.sh --via=vpn --last=100

# Фильтр по устройству + ключевое слово домена
sudo /etc/vpn-status.sh --device=192.168.1.50 --filter=steam

# Показать только соединения через провайдера
sudo /etc/vpn-status.sh --via=isp

# Расширить окно, если вывод пустой
sudo /etc/vpn-status.sh --last=200
```

### scripts/update-vpn-routes (развёртывается в /etc/update-vpn-routes)

**Синтаксис:** `sudo /etc/update-vpn-routes`

Обычно вызывается cron ежедневно в `CRON_UPDATE_HOUR:00` (по умолчанию 5:00). Можно запустить вручную для разовой принудительной загрузки.

Поведение:
- Загружает список RU-подсетей во временный файл
- Сравнивает SHA256-хеш с существующим `/etc/white-list.txt`
- Если хеши совпадают: завершается с кодом 0 (без перестройки и без прерывания работы)
- Если хеши различаются: атомарно заменяет файл, затем запускает `/etc/routing.sh --no-update`
- Если загрузка не удалась: завершается с кодом 0 (без уведомлений об ошибках cron; существующие маршруты остаются нетронутыми)
- При сбое загрузки также проверяет, не пропал ли маршрут к VPN-серверу (восстановление после смены carrier) — если пропал, перестраивает маршруты из существующего файла подсетей

Логирует через `logger -t "vpn-routes"` (видно в journald).

**Примеры:**

```bash
# Ручной разовый запуск
ssh pi4 "sudo /etc/update-vpn-routes"

# Проверить результат
ssh pi4 "sudo journalctl -t vpn-routes -n 10 --no-pager"

# Проверить расписание cron
ssh pi4 "sudo cat /etc/cron.d/vpn-routes"
# Ожидается: 0 5 * * * root /etc/update-vpn-routes >> /var/log/vpn-routes.log 2>&1
```

### scripts/watch-routes.py (развёртывается в /etc/watch-routes.py)

**Синтаксис:** `sudo /etc/watch-routes.py [--src IP] [--no-dns] [--tag {VPN,ISP,both}]`

Обогатитель логов iptables в реальном времени. Запускает `journalctl -f -k --no-pager -o short-iso` и разбирает строки `[VPN]`/`[ISP]` по мере их поступления. Разрешает IP-адреса назначения через кешированные rDNS-запросы (кеш в памяти, таймаут 2 секунды на запрос). Выводит обогащённые данные: временная метка, тег, исходный IP, IP-адрес назначения (с именем хоста), протокол и порт. Для остановки нажмите Ctrl+C.

Требует Python 3 (только стандартная библиотека — без pip-зависимостей).

**Флаги:**

| Флаг | Описание |
|------|----------|
| `--src IP` | Показывать только записи, где SRC совпадает с этим IP-адресом |
| `--no-dns` | Пропустить обратные DNS-запросы; отображать необработанные IP-адреса назначения |
| `--tag VPN\|ISP\|both` | Фильтр по тегу маршрутизации (по умолчанию: both) |

**Примеры:**

```bash
# Просмотр всех соединений в реальном времени
sudo /etc/watch-routes.py

# Наблюдение за VPN-трафиком одного устройства
sudo /etc/watch-routes.py --src 192.168.1.50 --tag VPN

# Без DNS-запросов для более быстрого вывода (полезно при высоком трафике)
sudo /etc/watch-routes.py --no-dns

# Наблюдение за всем трафиком через провайдера без DNS
sudo /etc/watch-routes.py --tag ISP --no-dns
```

## Решение проблем и известные нюансы

Каждая запись следует шаблону: **Симптом → Причина → Решение**.

---

**Устройства LAN не могут получить доступ к интернету (цепочка FORWARD сбрасывает пакеты)**

Симптом: После установки RPi как шлюза весь трафик LAN-устройств молча отбрасывается. Команда `ssh pi4 "sudo iptables -L FORWARD -n"` показывает политику по умолчанию `DROP` без правил ACCEPT.

Причина: Docker (если установлен на RPi) устанавливает политику по умолчанию для цепочки FORWARD равной DROP. Без явных правил ACCEPT никакой трафик LAN не проходит через RPi.

Решение: Повторно запустите `sudo /etc/routing.sh` — шаг 7c добавляет правила `FORWARD -i eth0 ACCEPT` и `FORWARD RELATED,ESTABLISHED ACCEPT`. Эти правила всегда заново применяются при каждом запуске routing.sh.

---

**В journald нет записей [VPN] или [ISP]**

Симптом: Команда `journalctl -k | grep -E '\[VPN\]|\[ISP\]'` ничего не возвращает, даже когда трафик LAN проходит через RPi.

Причина: Правила LOG должны добавляться в цепочку FORWARD **перед** правилами ACCEPT. LOG — нетерминирующее действие (продолжает к следующему правилу); ACCEPT — терминирующее. Если ACCEPT стоит первым, правило LOG никогда не достигается и записи в journald не пишутся.

Решение: Повторно запустите `sudo /etc/routing.sh` — шаг 7b добавляет правила LOG; шаг 7c добавляет правила ACCEPT в правильном порядке. Каждый запуск начинается со сброса правил, поэтому порядок всегда корректен после повторного запуска.

---

**Веб-интерфейс роутера недоступен с устройств LAN**

Симптом: Невозможно открыть `http://192.168.1.1` с устройств LAN после настройки RPi как шлюза.

Причина: Неограниченное правило MASQUERADE на `eth0` перезаписывает исходные IP-адреса для всего исходящего трафика — включая трафик внутри LAN к адресу `192.168.1.1`. Роутер видит все запросы как исходящие от `192.168.1.254` и блокирует их.

Решение: `routing.sh` на шаге 7 использует `! -d LAN_SUBNET` в правиле MASQUERADE для eth0, исключая внутрисетевой трафик из MASQUERADE. Повторно запустите `sudo /etc/routing.sh`, чтобы восстановить правильное правило.

---

**dnsmasq не запускается или конфликтует с существующей конфигурацией**

Симптом: Шаги 17/18 `deploy.sh` завершаются ошибкой; `systemctl status dnsmasq` показывает ошибку разбора конфигурации или конфликт портов.

Причина: Если конфигурация `dnsmasq` развёртывается до установки пакета, `apt-get install dnsmasq` перезапишет развёрнутую конфигурацию конфигурацией по умолчанию пакета или запустит интерактивный запрос.

Решение: Повторно запустите `./deploy.sh` — шаг 17 всегда устанавливает `dnsmasq` перед шагом 18, который развёртывает конфигурацию. Установка использует `DEBIAN_FRONTEND=noninteractive`, чтобы исключить интерактивные запросы.

---

**Поднятие туннеля завершается ошибкой или `awg-quick up awg0` возвращает "already exists"**

Симптом: `sudo awg-quick up awg0` завершается ошибкой "RTNETLINK answers: File exists" или аналогичной; либо интерфейс находится в неизвестном состоянии.

Причина: `awg-quick up` не идемпотентен. `deploy.sh` намеренно не поднимает туннель по этой причине (см. раздел о развёртывании).

Решение: Сначала опустите интерфейс, затем поднимите снова:

```bash
ssh pi4 "sudo awg-quick down awg0 && sudo awg-quick up awg0"
```

Или перезапустите через systemd:

```bash
ssh pi4 "sudo systemctl restart awg-quick@awg0"
```

---

**vpn-status.sh не показывает записей даже после просмотра сайтов**

Симптом: Вывод `vpn-status.sh` показывает `(no connections matched — try --last=200 or remove filters)`, хотя устройства LAN генерируют трафик.

Причина A: dnsmasq не настроен как DNS-сервер в роутере — DNS-запросы обходят RPi полностью, поэтому у dnsmasq нет журнала для сопоставления. (Это напрямую не подавляет записи `[VPN]`/`[ISP]`, но стоит проверить в первую очередь.)

Причина B: LAN-устройство не обновило DHCP-аренду после смены шлюза в роутере — оно всё ещё использует старый шлюз (например, `192.168.1.1` напрямую), и трафик не проходит через RPi.

Решение: В веб-интерфейсе роутера: откройте настройки DHCP/LAN → установите «Адрес шлюза» равным `192.168.1.254`. Затем обновите DHCP-аренду на LAN-устройстве (переподключите Wi-Fi или выполните `ipconfig /renew` на Windows). Также установите DNS-сервер равным `192.168.1.254` на той же странице настроек.

---

**Столбец DOMAIN в vpn-status.sh показывает IP-адреса вместо доменных имён**

Симптом: В столбце DOMAIN вывода `vpn-status.sh` отображаются IP-адреса вместо доменных имён.

Причина: dnsmasq не является DNS-сервером для LAN-устройств. DNS-запросы уходят напрямую к вышестоящему резолверу, минуя журнал запросов dnsmasq. Без записей в журнале dnsmasq `vpn-status.sh` не может сопоставить IP-адреса назначения с доменными именами; резервный rDNS-поиск также не работает для CDN-адресов (нет PTR-записей).

Решение: Установите DNS-сервер в роутере равным `192.168.1.254` (см. «Требования и подготовка» → DHCP на роутере). После обновления аренды DNS-запросы LAN начнут проходить через dnsmasq, который журналирует их для сопоставления.

---

**Маршруты раздельной маршрутизации пропадают после перезагрузки роутера (смена carrier в NM)**

Симптом: Маршрутизация через VPN ломается после перезагрузки роутера или пропадания и восстановления канала на eth0. Команда `ssh pi4 "ip route show | wc -l"` показывает приблизительно 2 (только локальные маршруты). `ip route get 8.8.8.8` больше не показывает `dev awg0`.

Причина: Когда роутер перезагружается, канал eth0 пропадает (событие смены carrier). NetworkManager (NM) сбрасывает все маршруты eth0 при событии опускания канала — включая ~1360 маршрутов RU-подсетей и маршрут к VPN-серверу, добавленных `routing.sh`. Когда eth0 поднимается снова, NM восстанавливает только локальный маршрут для канала. Без маршрута к VPN-серверу (`YOUR_VPN_SERVER_IP/32 via 192.168.1.1`) команда `ip route get YOUR_VPN_SERVER_IP` разрешается через `awg0` (таблица политик 51820), создавая петлю маршрутизации. Нет VPN → нет интернета → ежедневная загрузка через cron тоже не работает → система не может самовосстановиться без вмешательства.

Решение: Шаг 22 `deploy.sh` развёртывает `/etc/NetworkManager/dispatcher.d/10-vpn-routes` — скрипт NM-диспетчера, который автоматически восстанавливает маршруты, запуская `routing.sh --no-update` в фоне при обнаружении события `eth0 up`.

Проверка работы диспетчера:

```bash
ssh pi4 "sudo journalctl -t vpn-routes -n 5 --no-pager"
# Ожидаемый вывод: "eth0 up — restoring VPN split-tunnel routes"
```

Резервный механизм: `update-vpn-routes` также проверяет наличие маршрута к VPN-серверу при сбое загрузки и запускает перестройку. Оба механизма развёртываются командой `./deploy.sh`.

Если маршруты уже пропали и требуется ручное восстановление:

```bash
ssh pi4 "sudo /etc/routing.sh"
```
