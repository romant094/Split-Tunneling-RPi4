11. ## Troubleshooting & Known Gotchas — per D-14 and D-15, symptom→cause→fix format (3-line pattern per entry, no prose paragraphs). Include at minimum these 5 gotchas extracted from .planning/STATE.md §"Phase 4 Post-execution Fixes":

    **LAN devices cannot reach internet at all (FORWARD chain DROP)**
    Symptom: All LAN traffic silently dropped; `iptables -L FORWARD -n` shows policy DROP.
    Cause: Docker sets FORWARD chain default policy to DROP. routing.sh ACCEPT rules were not present in early versions.
    Fix: Re-run `sudo /etc/routing.sh` — Stage 7c adds `FORWARD -i eth0 ACCEPT` and `FORWARD RELATED,ESTABLISHED ACCEPT` rules.

    **No [VPN] or [ISP] entries in journald**
    Symptom: `journalctl -k | grep -E '\[VPN\]|\[ISP\]'` returns nothing after traffic flows through RPi.
    Cause: LOG rules must be added BEFORE ACCEPT rules in the FORWARD chain. ACCEPT terminates rule traversal; if ACCEPT is first, LOG never fires.
    Fix: routing.sh Stage 7b adds LOG before Stage 7c adds ACCEPT. Re-run `sudo /etc/routing.sh` to restore correct order.

    **Keenetic router web/app admin becomes inaccessible from LAN devices**
    Symptom: Cannot reach 192.168.1.1 from LAN devices after RPi is set as gateway.
    Cause: MASQUERADE on eth0 without LAN subnet exclusion rewrites source IPs; Keenetic sees all requests from 192.168.1.254 and blocks them as spoofed.
    Fix: routing.sh Stage 7 uses `! -d LAN_SUBNET` in the eth0 MASQUERADE rule. Re-run `sudo /etc/routing.sh`.

    **dnsmasq fails to start or conflicts with existing config**
    Symptom: Stage 18 fails; systemctl status dnsmasq shows config parse error or port conflict.
    Cause: deploy.sh Stage 17 installs dnsmasq before Stage 18 deploys config. If order was reversed in an older deploy, apt would prompt interactively or overwrite our config.
    Fix: re-run `./deploy.sh` — Stage 17 always runs before Stage 18.

    **Tunnel bring-up fails or `awg-quick up awg0` returns "already up"**
    Symptom: `sudo awg-quick up awg0` errors with "already exists" or interface is in unknown state.
    Cause: awg-quick up is not idempotent; deploy.sh intentionally does not bring up the tunnel (Pitfall 5).
    Fix: `sudo awg-quick down awg0 && sudo awg-quick up awg0` to reset; or `sudo systemctl restart awg-quick@awg0`.

    Also add:
    **vpn-status.sh shows no entries even after browsing the web**
    Symptom: vpn-status.sh output shows "(no connections matched — try --last=200 or remove filters)".
    Cause: dnsmasq is not configured as the DNS server in Keenetic; OR LAN device is not using RPi as gateway yet (Keenetic DHCP lease not renewed).
    Fix: In Keenetic web UI: Home network → Segments → Default → DNS server → set to 192.168.1.254. Then renew DHCP lease on LAN device (disconnect/reconnect Wi-Fi or `ipconfig /renew`).

    **Domain column in vpn-status.sh shows raw IPs instead of hostnames**
    Symptom: DOMAIN column shows IP addresses, not hostnames.
    Cause: dnsmasq is not the DNS server for LAN devices (see above); dnsmasq has no query log to correlate against; rDNS fallback also fails for CDN IPs.
    Fix: Set Keenetic DNS to 192.168.1.254 (dnsmasq) as described above.

    **Split-tunnel routes disappear after Keenetic reboots (NM carrier-change)**
    Symptom: VPN routing breaks after router reboot; `ip route show | wc -l` drops to ~2; `ip route get 8.8.8.8` no longer shows `dev awg0`.
    Cause: Keenetic reboot drops eth0 carrier. NM flushes all eth0 routes on carrier-change (link down → link up), including the VPN server host route and all ~1360 RU CIDR routes added by routing.sh. Without the VPN server host route, `ip route get YOUR_VPN_SERVER_IP` resolves via awg0 (policy table 51820) — creating a routing loop that prevents VPN reconnection. No VPN → no internet → cron download failure → no self-heal.
    Fix: NM dispatcher at `/etc/NetworkManager/dispatcher.d/10-vpn-routes` (deployed by deploy.sh Stage 22) auto-restores routes on `eth0 up` by running `routing.sh --no-update` in background. Verify: `sudo journalctl -t vpn-routes -n 5 --no-pager` — expect "eth0 up — restoring VPN split-tunnel routes". Fallback: `update-vpn-routes` also checks for missing VPN server host route and rebuilds if absent. See quick task 260523-nmr for full incident timeline.
