<objective>
Make the RPi VPN gateway survive reboot. After this plan, a fresh power-cycle of the RPi brings the AmneziaWG tunnel up automatically AND triggers `/etc/routing.sh` to rebuild split-tunnel routes — no manual intervention. This delivers the autostart vertical slice (boot → tunnel → routes → reachability) covering AUTO-01, AUTO-02, and unblocks the post-reboot verification checks VRFY-01..04.

Purpose: The current Phase 1+2 stack requires manual `awg-quick up awg0` + `sudo /etc/routing.sh` after every boot. This plan wires both into systemd so the gateway is fully autonomous across reboots.

Output: A new systemd unit file at `systemd/vpn-routing.service` and extension of `deploy.sh` to SCP that unit file, run `systemctl daemon-reload`, and enable both `awg-quick@awg0` (template unit shipped with amneziawg-tools) and `vpn-routing.service`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| macOS workstation → RPi over SSH | Deploy.sh ships systemd/vpn-routing.service to /tmp on the RPi, then sudo-moves it into /etc/systemd/system/. Path is under root control end-to-end (BatchMode=yes, key auth only). |
| systemd ↔ /etc/routing.sh | vpn-routing.service ExecStart launches /etc/routing.sh as root. The script itself was deployed and chmoded in Phase 2; this plan does not alter that boundary. |
| boot ordering: awg-quick@awg0 → vpn-routing.service | Requires= + After= are systemd's first-class dependency primitives; misconfiguration here causes loss of availability, not loss of confidentiality. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Tampering | systemd/vpn-routing.service in transit (SCP) | mitigate | SCP to /tmp staging then `sudo mv` + `sudo chmod 644` + `sudo chown root:root` (D-11). Same pattern proven in Phase 1/2 deploys. SSH host key in ~/.ssh/known_hosts pins the RPi identity. |
| T-03-02 | Tampering | /etc/systemd/system/vpn-routing.service on RPi | mitigate | Mode 644 + root:root ownership enforced by deploy.sh Stage 12. Non-root processes cannot modify. |
| T-03-03 | Elevation of Privilege | vpn-routing.service ExecStart runs /etc/routing.sh as root | accept | This is the intended privilege model. /etc/routing.sh is root-owned (deployed by Phase 2). Service has no `User=` directive, so systemd default is root — required for `ip route` and `iptables` calls inside routing.sh. |
| T-03-04 | Denial of Service | Boot-time download failure could cascade | mitigate | D-01 unit calls `/etc/routing.sh` (no flags); routing.sh has D-04 fallback to existing /etc/vpn-ru-subnets.txt. No Restart= directive on the unit (Anti-Pattern: storm risk). |
| T-03-05 | Denial of Service | Tunnel handshake race vs vpn-routing.service start | accept | Pitfall 1: handshake completes 1-2s after `awg-quick up awg0` exits. Brief packet loss at boot is acceptable for a gateway; clients retry. No `ExecStartPost=sleep` workaround (code smell). |
| T-03-06 | Information Disclosure | vpn-routing.service unit content | accept | Unit file contains no secrets; only paths and systemd directives. Mode 644 (world-readable) is correct for systemd unit files. |
| T-03-SC | Tampering | Supply chain — package installs | accept | This plan installs NO new packages. amneziawg-tools (Phase 1), iptables-persistent (Phase 2) already on RPi. No package legitimacy gate needed. |
</threat_model>
