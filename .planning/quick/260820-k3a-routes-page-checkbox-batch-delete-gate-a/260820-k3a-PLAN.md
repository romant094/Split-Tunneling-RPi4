# Quick Task 260820-k3a — Routes page

Part B of a three-part batch. Part A (`260820-juc`) landed the backend
`routes_dirty` flag this part consumes.

## Task 1 — Checkbox column and batch delete

**Files:** `src/admin/src/components/ui/checkbox.jsx` (new),
`src/admin/src/pages/Routes.jsx`

**Action.**
1. Add a `Checkbox` UI component. Native `<input type="checkbox">` styled with
   the project's tokens — no new dependency, and `indeterminate` is settable via
   a ref, which the header checkbox needs for a partial selection.
2. `RouteSection` gains a `selected` Set of CIDRs. Leading checkbox column in
   both header and body.
3. Header checkbox operates on `sorted` — the filtered, sorted view — so
   "select all" under an active filter means "all matching rows", not the whole
   file. Checked when every visible row is selected, indeterminate when some are.
4. Prune the selection whenever the visible set changes: a CIDR that has been
   filtered out or deleted server-side must not stay silently selected and get
   removed by a later batch delete.
5. Selection bar above the table: `N selected`, `Delete N`, `Clear`.
6. `DeleteConfirmDialog` extended to take a list. One CIDR keeps today's wording;
   several show the count and a scrollable preview of what will go.
7. Batch delete issues **sequential** DELETEs. Each rewrites the whole route file
   server-side, so concurrent writes would drop entries — the same constraint
   already documented on `flushStagedDescriptions`. Report partial failure
   honestly (`Removed X of N`) rather than assuming success.

**Verify.** `npm run lint` and `npm run build` in `src/admin`.

**Done.** Multiple routes can be removed in one pass; the confirm dialog states
exactly what will be deleted; a failure mid-batch is surfaced.

## Task 2 — Gate Apply Changes on real pending work

**Files:** `src/admin/src/pages/Routes.jsx`, `src/admin/src/routeStaging.js`

**Action.**
1. `RoutesPage` subscribes to the staging store and polls `/api/status` for
   `routes_dirty`.
2. Button enabled iff `routes_dirty || staged adds || staged description edits`.
   Disabled state gets a title explaining why, so a greyed-out button is never a
   mystery.
3. After a successful apply, use the `routes_dirty` echoed by
   `/api/config/apply` (added in Part A) to settle the button immediately instead
   of waiting for the next poll.
4. Mutations made from this page (`handleAdd`, `handleEdit`, `handleDelete`,
   `handleBulkAdd`) write to the server immediately, so they must flip the button
   back on without waiting for a poll either. Add a local override that the next
   authoritative status read supersedes.
5. Tolerate a missing `routes_dirty` field: an older backend must leave the
   button enabled, never permanently disabled.

**Verify.** `npm run lint`, `npm run build`. Reason through: fresh load with
nothing pending → disabled; add a route → enabled; apply → disabled; staged
entry from the Logs page → enabled.

**Done.** The button is dark only when there is genuinely nothing to apply, and
the state survives a reload.

## Task 3 — Fill Descriptions scope dialog

**Files:** `src/admin/src/pages/Routes.jsx`

**Action.**
1. Clicking `Fill Descriptions` opens `FillDescriptionsDialog` instead of
   starting work immediately.
2. Two choices: **Only missing (N)** — default, today's behaviour — and
   **All routes (M)**, which re-looks-up and overwrites existing descriptions.
3. The "all" choice carries a warning that existing descriptions will be
   replaced, noting that the edits land in staging and are visible in
   `DiffPreview` until Apply, so declining to apply is the undo.
4. Both counts are shown up front — lookups are sequential, one request per
   route, so the user should see the cost before starting.
5. Scope wording: the existing code targets `sorted`, i.e. the filtered view. The
   dialog says so explicitly when a filter is active, and speaks of the whole
   list when it is not.
6. Disable `Fill` when the chosen scope is empty.

**Verify.** `npm run lint`, `npm run build`.

**Done.** The button no longer starts a long job on a single click, and the two
scopes are distinguishable before committing to one.
